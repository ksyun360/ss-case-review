# Phase 4 collaborator update

Date: October 18, 2026. Status: Phase 4 remains in progress. The application is not ready for court testing or real records.

## Shareable update

The project includes a responsive navigation and document-selection preview, source-location validation, private original-file storage, versioned PostgreSQL case metadata, and a runnable synthetic-only case API. The backend creates drafts and lists or opens cases according to the configured reviewer's membership. An internal [original-ingestion service](original-ingestion.md) links bounded byte streams to membership-scoped PostgreSQL references. A [persistent attempt journal](upload-journal.md) records versions before receipt and tracks tested success and failure paths. Successful original registration now advances the case revision atomically and records the registered document in a case-scoped revision-event table. The browser can create a synthetic draft, list saved labels and revisions, and open a case page that lists registered original version IDs and byte counts through the local development API.

The case API assigns case IDs and ownership on the server, validates inputs, restricts development requests, and returns safe error codes. An opt-in route accepts a bounded synthetic original byte stream for a member case and rejects oversized or unsupported-media requests safely. The route now reserves fixed PDF extraction work before acknowledging the original. A second opt-in route returns exact original bytes as a forced attachment only after a membership-filtered lookup. Guarded startup enables the original routes only when the developer supplies a dedicated absolute storage root; the default remains metadata-only. Startup opens a bounded loopback PostgreSQL pool, runs migrations, and binds the API on loopback only. Native PostgreSQL tests confirm case persistence and membership filtering, including access after a membership change. A separate real-process smoke check confirmed synthetic case creation and listing across an API restart. The browser displays loading, empty, unavailable/retry, and populated case-list states. A case page distinguishes an inaccessible case from a temporary service failure. The upload screen registers selected synthetic originals in one new draft and shows per-file progress when the opt-in route is available. The screen does not extract or review documents during the request.

Phase 4 is not complete. The remaining implementation includes durable uploads and background processing, OCR and broader format coverage, complete source-linked review artifacts, and revision history. The source repository now persists PDF view, rotation, text-item transforms, dimensions, and UTF-16 ranges; current tests do not establish record accuracy, completeness, or processing latency. A revision-scoped correction-suggestion repository, guarded API, browser client, and case-page desk now record proposed artifact-entry changes without modifying extracted source values or the case revision; reviewers can accept or reject pending suggestions through the guarded status route.

Internal [document-inspection modules](document-inspection.md) now identify PDF and classic TIFF signatures, parse a synthetic PDF's page count, and extract native text page by page through PDF.js. A bounded byte-to-pages adapter owns parser loading and cleanup while preserving byte and page policy failures. A [synthetic processing coordinator](original-processing.md) verifies registered original bytes, PDF admission, fixed extraction gaps, and atomic source publication. A concrete entry point connects the coordinator to the bounded PDF.js adapter; a real-filesystem regression verifies exact persisted text and provenance from a structurally valid two-page synthetic PDF. The extractor retains physical page numbers, UTF-16 offsets, and parser geometry; lower-level tests exercise a three-page synthetic fixture with tagged content, multiple lines, and an empty page. Required budgets reject oversized inspection input before parser creation and oversized extraction documents before page reads. A separate regression verifies safe unavailable-page results and retention of successful pages after loading, text, or cleanup failures. A durable processing journal and callable one-job worker now persist queued, processing, published, and failed states. Worker scheduling, isolation, text/time/memory budgets, OCR, and broader format coverage remain pending.

An internal [text-source repository](text-source-storage.md) now stores and retrieves synthetic page text with original hash metadata, case revision, extraction version, a stable source-unit UUID, and persisted PDF geometry. One PostgreSQL statement can publish an authorized document's complete page set or publish no pages when any candidate loses authorization or provenance alignment. A regression validates a Unicode quotation against text returned through member-scoped SQL retrieval. A metadata-only inventory returns current member-case sources in stable physical page order without page text. A fourth PostgreSQL migration adds the geometry column with a safe empty default. Guarded inventory and source-read APIs now return geometry, metadata, or exact stored text with validated identifiers and safe failures. A guarded citation route rechecks a proposed quote and UTF-16 span against the authorized persisted page and returns a located span or a safe mismatch reason. Browser clients validate geometry when the API supplies it, reject raw text in inventory rows, and return exact page text only for a known source. The case screen discovers sources and displays selected exact text with physical-page and provenance metadata. Extraction workers remain limited to native PDF text; the viewer still needs geometry overlays, OCR, broader format coverage, and complete review functionality.

The development team will continue with durable synthetic document transfer, source provenance, and source-grounded generation before requesting full application qualification. Validated claims may now carry structured chronology fields; the medical and procedural sections render those fields in source-linked tables and keep missing fields visibly marked for investigation. Court IT must approve deployment, identity, certificate/PACER requirements, and the model data path before real-record testing. Hosted CI and repository protections remain scheduled for Phase 3 at the very end, before pilot handoff.

## Current evidence

The October 19 geometry increment passes 307 fast tests, 10 native PostgreSQL tests, and a 100% full mutation score across 3,060 mutants. The current coverage report is 99.22% statements, 98.22% branches, 100% functions, and 99.78% lines.

The case page now exposes a member-scoped processing overview that summarizes each registered document as Ready, Needs review, Reading, or Queued. The overview has explicit loading, retry, empty, and case-change states.

The local gate passes 307 fast unit/integration tests, 10 native PostgreSQL tests, and 9 standalone Chromium workflows. A native PostgreSQL test also launches Chromium and verifies one small synthetic original through the local proxy, API, metadata repository, and private storage. Current first-party source coverage reaches 99.31% statements, 98.28% branches, 100% functions, and 99.78% lines; the full mutation gate reaches a 100% score across 2,965 mutants. The API checks verify that existing original, processing, and source records from another reviewer's case return 404; source-repository regressions deny another reviewer's write, read, and inventory access without changing existing text. A serial scheduler regression verifies bounded leases, nonoverlapping worker calls, error containment, and clean shutdown. Browser clients and the source workspace validate source inventory, exact source identity, and provenance before returning or displaying stored text. The source workspace now accepts a proposed quotation, verifies its exact UTF-16 span through the guarded API, highlights only the verified range in the persisted page text, and safely rejects invalid cited spans from claim links. A reviewer can open the authorized original PDF beside the selected source text with the physical-page fragment preserved. Production artifact sections now provide case-insensitive search over validated classified claims without changing source values; the sections show speaker context, verified source links, safe unverified wording, loading, unavailable, empty, and no-match states without inventing entries. The upload screen can retry an uncertain file transfer, resume the remaining queue, and re-enable retry after another failed attempt. Production case sections now include a curated reference desk with official eCFR and SSA links plus a MedlinePlus medical reference, explicitly separated from case evidence. Persisted claims now preserve approved artifact section and speaker labels, reject unknown labels before publication, and display the context next to the verified claim. The demo chronology supports a local correction suggestion without replacing source values, and the procedural chronology lets a reviewer toggle milestone emphasis and choose a presentation-only event group. The demo reference desk links to curated SSA, eCFR, and MedlinePlus material while labeling reference material separately from evidence. These measurements cover implemented code, not the unfinished application. The separate 320-pixel case-navigation test still intercepts API responses. Read the [build-status report](build-status.md), [development startup guide](development-server.md), and [case API contract](case-api.md) for scope and limitations.

The current browser preview supports synthetic case-metadata feedback, opt-in synthetic original registration, a member-scoped original inventory, exact-text source viewing, an inline member-scoped PDF viewer, original-document opening in a new tab, and per-original background-processing status. The development proxy forwards case, capability, original, processing, and source requests to the loopback API when both processes run. One automated Chromium-to-native-PostgreSQL round trip verifies a small synthetic file and its exact stored bytes; broader file types, volume, and recovery remain unverified. The case page shows version IDs, byte counts, and validated queued, processing, published, failed, missing, or unavailable status. Queued and processing rows poll every two seconds; terminal, missing, and unavailable states stop polling, and navigation cancels stale timers and responses. The browser renders the retrieved PDF beside the original inventory and displays persisted validated, refused, invalid, empty, and unverified claim results with investigation-safe wording. Verified claims now link to a matching persisted source entry, and the source workspace opens the cited page from the link hash, highlights the validated span when the span remains within the persisted page, and opens the authorized original PDF beside that text with a `#page=` fragment for the physical source page. The workspace also renders an accessible page-alignment overlay from persisted geometry regions for the selected source. Invalid, negative, zero-length, and out-of-bounds spans remain unhighlighted. The production case page now provides Summary, Medical chronology, Procedural chronology, and Five-step review links with explicit empty, loading, unavailable, and source-grounded classified-claim states. The server validates a strict Gemini claim envelope against authorized source units, preserves generated claim text, persists validated results with the published processing revision, and returns investigation-safe statuses for unmatched citations; guarded startup passes a configured generator into the scheduler and worker. Full review-artifact generation remains pending. The upload screen warns when draft creation or a file transfer cannot be confirmed, blocks immediate duplicate submission, and locks the selected files during registration. The workflow still lacks reconciliation, artifact source maps, and broader format processing. No developer credential, real case record, or live model request enters the deterministic checks. No shared deployment or PR has occurred.
