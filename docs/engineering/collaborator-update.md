# Phase 4 collaborator update

Date: September 28, 2026. Status: Phase 4 remains in progress. The application is not ready for court testing or real records.

## Shareable update

The project includes a responsive navigation and document-selection preview, source-location validation, private original-file storage, versioned PostgreSQL case metadata, and a runnable synthetic-only case API. The backend creates drafts and lists or opens cases according to the configured reviewer's membership. An internal [original-ingestion service](original-ingestion.md) links bounded byte streams to membership-scoped PostgreSQL references. A [persistent attempt journal](upload-journal.md) records versions before receipt and tracks tested success and failure paths. The browser can create a synthetic draft, list saved labels and revisions, and open a case page that lists registered original version IDs and byte counts through the local development API.

The case API assigns case IDs and ownership on the server, validates inputs, restricts development requests, and returns safe error codes. An opt-in route accepts a bounded synthetic original byte stream for a member case and rejects oversized or unsupported-media requests safely. A second opt-in route returns exact original bytes as a forced attachment only after a membership-filtered lookup. Guarded startup enables the original routes only when the developer supplies a dedicated absolute storage root; the default remains metadata-only. Startup opens a bounded loopback PostgreSQL pool, runs migrations, and binds the API on loopback only. Native PostgreSQL tests confirm case persistence and membership filtering, including access after a membership change. A separate real-process smoke check confirmed synthetic case creation and listing across an API restart. The browser displays loading, empty, unavailable/retry, and populated case-list states. A case page distinguishes an inaccessible case from a temporary service failure. The upload screen registers selected synthetic originals in one new draft and shows per-file progress when the opt-in route is available. The screen does not extract or review documents.

Phase 4 is not complete. The remaining implementation includes durable uploads and background processing, document extraction/OCR, source viewing and highlighting, Gemini integration, the four source-linked review views, corrections, and approved reference lookups. Current tests do not establish record accuracy, completeness, or processing latency.

Internal [document-inspection modules](document-inspection.md) now identify PDF and classic TIFF signatures, parse a synthetic PDF's page count, and extract native text page by page through PDF.js. The extractor retains physical page numbers, UTF-16 offsets, and parser geometry; the tests exercise a three-page synthetic fixture with tagged content, multiple lines, and an empty page. A required extraction page budget rejects oversized documents before page reads. A separate regression verifies safe unavailable-page results and retention of successful pages after loading, text, or cleanup failures. These modules do not run during upload, supply browser source links, or establish file safety. Worker isolation, byte/text/time/memory budgets, OCR, format coverage, and persisted inspection states remain pending.

The development team will continue with durable synthetic document transfer and source provenance before requesting full application qualification. Court IT must approve deployment, identity, certificate/PACER requirements, and the model data path before real-record testing. Hosted CI and repository protections remain scheduled for Phase 3 at the very end, before pilot handoff.

## Current evidence

The local gate passes 221 fast unit/integration tests, 10 native PostgreSQL tests, and 9 standalone Chromium workflows. A native PostgreSQL test also launches Chromium and verifies one small synthetic original through the local proxy, API, metadata repository, and private storage. Current first-party source coverage reaches 100% across the four measured metrics; the full mutation gate reaches a 100% score. The API checks verify that an existing original from another reviewer's case returns 404 without a private-storage read. These measurements cover implemented code, not the unfinished application. The separate 320-pixel case-navigation test still intercepts API responses. Read the [build-status report](build-status.md), [development startup guide](development-server.md), and [case API contract](case-api.md) for scope and limitations.

The current browser preview supports synthetic case-metadata feedback, opt-in synthetic original registration, and a member-scoped original inventory. The development proxy forwards case, capability, and original requests to the loopback API when both processes run. One automated Chromium-to-native-PostgreSQL round trip verifies a small synthetic file and its exact stored bytes; broader file types, volume, and recovery remain unverified. The case page shows version IDs and byte counts with loading, empty, unavailable, and retry feedback. The API can return a member-visible original as an attachment, but the browser has no original download control, source viewer, page navigation, or highlights. The upload screen warns when draft creation or a file transfer cannot be confirmed, blocks immediate duplicate submission, and locks the selected files during registration. The workflow still lacks confirmed retry, reconciliation, document inspection, processing, and source links. No developer credential, real case record, or live model request enters the deterministic checks. No shared deployment or PR has occurred.

The private storage adapter and internal ingestion service accept bounded byte streams and maintain a persistent attempt journal. An opt-in synthetic HTTP route invokes the service in isolated API tests; guarded startup exposes the route only with an explicit storage root. The API reports that configuration as a Boolean, and the upload screen displays available, disabled, or unavailable status without exposing the storage path. The browser-client helper sends one selected synthetic `File` to the route and validates the returned receipt. The upload screen calls that helper sequentially for selected files and preserves the known draft link after a transfer failure. A failed creation request prompts the user to check saved cases; a failed transfer marks the affected file unconfirmed and stops later transfers. The screen does not retry automatically or reconcile the uncertain result. A bounded query identifies stale receiving attempts, but no recovery worker acts on those attempts. Crash recovery and directory synchronization remain incomplete. The next milestones are broader transfer qualification and source provenance. Neither milestone alone completes the upload-to-review features.
