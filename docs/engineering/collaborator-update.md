# Phase 4 collaborator update

Date: October 4, 2026. Status: Phase 4 remains in progress. The application is not ready for court testing or real records.

## Shareable update

The project includes a responsive navigation and document-selection preview, source-location validation, private original-file storage, versioned PostgreSQL case metadata, and a runnable synthetic-only case API. The backend creates drafts and lists or opens cases according to the configured reviewer's membership. An internal [original-ingestion service](original-ingestion.md) links bounded byte streams to membership-scoped PostgreSQL references. A [persistent attempt journal](upload-journal.md) records versions before receipt and tracks tested success and failure paths. The browser can create a synthetic draft, list saved labels and revisions, and open a case page that lists registered original version IDs and byte counts through the local development API.

The case API assigns case IDs and ownership on the server, validates inputs, restricts development requests, and returns safe error codes. An opt-in route accepts a bounded synthetic original byte stream for a member case and rejects oversized or unsupported-media requests safely. The route now reserves fixed PDF extraction work before acknowledging the original. A second opt-in route returns exact original bytes as a forced attachment only after a membership-filtered lookup. Guarded startup enables the original routes only when the developer supplies a dedicated absolute storage root; the default remains metadata-only. Startup opens a bounded loopback PostgreSQL pool, runs migrations, and binds the API on loopback only. Native PostgreSQL tests confirm case persistence and membership filtering, including access after a membership change. A separate real-process smoke check confirmed synthetic case creation and listing across an API restart. The browser displays loading, empty, unavailable/retry, and populated case-list states. A case page distinguishes an inaccessible case from a temporary service failure. The upload screen registers selected synthetic originals in one new draft and shows per-file progress when the opt-in route is available. The screen does not extract or review documents during the request.

Phase 4 is not complete. The remaining implementation includes durable uploads and background processing, document extraction/OCR, source viewing and highlighting, Gemini integration, the four source-linked review views, corrections, and approved reference lookups. Current tests do not establish record accuracy, completeness, or processing latency.

Internal [document-inspection modules](document-inspection.md) now identify PDF and classic TIFF signatures, parse a synthetic PDF's page count, and extract native text page by page through PDF.js. A bounded byte-to-pages adapter owns parser loading and cleanup while preserving byte and page policy failures. A [synthetic processing coordinator](original-processing.md) verifies registered original bytes, PDF admission, fixed extraction gaps, and atomic source publication. A concrete entry point connects the coordinator to the bounded PDF.js adapter; a real-filesystem regression verifies exact persisted text and provenance from a structurally valid two-page synthetic PDF. The extractor retains physical page numbers, UTF-16 offsets, and parser geometry; lower-level tests exercise a three-page synthetic fixture with tagged content, multiple lines, and an empty page. Required budgets reject oversized inspection input before parser creation and oversized extraction documents before page reads. A separate regression verifies safe unavailable-page results and retention of successful pages after loading, text, or cleanup failures. A durable processing journal and callable one-job worker now persist queued, processing, published, and failed states. Worker scheduling, isolation, text/time/memory budgets, OCR, and broader format coverage remain pending.

An internal [text-source repository](text-source-storage.md) now stores and retrieves synthetic page text with original hash metadata, case revision, extraction version, and a stable source-unit UUID. One PostgreSQL statement can publish an authorized document's complete page set or publish no pages when any candidate loses authorization or provenance alignment. A regression validates a Unicode quotation against text returned through member-scoped SQL retrieval. A metadata-only inventory returns current member-case sources in stable physical page order without page text. A third PostgreSQL migration supplies the source table and constraints. Guarded inventory and source-read APIs now return metadata or exact stored text with validated identifiers and safe failures. A guarded citation route rechecks a proposed quote and UTF-16 span against the authorized persisted page and returns a located span or a safe mismatch reason. Browser clients validate every inventory and direct-source field, reject raw text in inventory rows, and return exact page text only for a known source. The case screen discovers sources and displays selected exact text with physical-page and provenance metadata. Extraction workers remain disconnected from this table; the viewer has no original-page image or geometry highlight, and storage plus matching alone does not establish source accuracy or complete review functionality.

The development team will continue with durable synthetic document transfer and source provenance before requesting full application qualification. Court IT must approve deployment, identity, certificate/PACER requirements, and the model data path before real-record testing. Hosted CI and repository protections remain scheduled for Phase 3 at the very end, before pilot handoff.

## Current evidence

The local gate passes 250 fast unit/integration tests, 10 native PostgreSQL tests, and 9 standalone Chromium workflows. A native PostgreSQL test also launches Chromium and verifies one small synthetic original through the local proxy, API, metadata repository, and private storage. Current first-party source coverage reaches 100% across the four measured metrics; the full mutation gate reaches a 100% score. The API checks verify that existing original, processing, and source records from another reviewer's case return 404; source-repository regressions deny another reviewer's write, read, and inventory access without changing existing text. A serial scheduler regression verifies bounded leases, nonoverlapping worker calls, error containment, and clean shutdown. Browser clients and the source workspace validate source inventory, exact source identity, and provenance before returning or displaying stored text. The source workspace now accepts a proposed quotation, verifies its exact UTF-16 span through the guarded API, and highlights only the verified range in the persisted page text. These measurements cover implemented code, not the unfinished application. The separate 320-pixel case-navigation test still intercepts API responses. Read the [build-status report](build-status.md), [development startup guide](development-server.md), and [case API contract](case-api.md) for scope and limitations.

The current browser preview supports synthetic case-metadata feedback, opt-in synthetic original registration, a member-scoped original inventory, exact-text source viewing, original-document opening, and per-original background-processing status. The development proxy forwards case, capability, original, processing, and source requests to the loopback API when both processes run. One automated Chromium-to-native-PostgreSQL round trip verifies a small synthetic file and its exact stored bytes; broader file types, volume, and recovery remain unverified. The case page shows version IDs, byte counts, and validated queued, processing, published, failed, missing, or unavailable status. Queued and processing rows poll every two seconds; terminal, missing, and unavailable states stop polling, and navigation cancels stale timers and responses. The browser now opens a member-scoped original as a new document tab, but it does not yet render page geometry, connect artifact citations to original pages, or provide geometry highlights. The upload screen warns when draft creation or a file transfer cannot be confirmed, blocks immediate duplicate submission, and locks the selected files during registration. The workflow still lacks confirmed upload retry, reconciliation, artifact source links, and broader format processing. No developer credential, real case record, or live model request enters the deterministic checks. No shared deployment or PR has occurred.

The private storage adapter and internal ingestion service accept bounded byte streams and maintain a persistent upload attempt journal. An opt-in synthetic HTTP route invokes the queued service in isolated API tests; guarded startup exposes the route only with an explicit storage root. The API reports that configuration as a Boolean, and the upload screen displays available, disabled, or unavailable status without exposing the storage path. The browser-client helper sends one selected synthetic `File` to the route and validates the returned receipt. The upload screen calls that helper sequentially for selected files and preserves the known draft link after a transfer failure. A failed creation request prompts the user to check saved cases; a failed transfer marks the affected file unconfirmed and stops later transfers. The screen does not retry automatically or reconcile the uncertain result. Guarded startup marks at most 25 still-receiving attempts older than 15 minutes failed and removes each exact synthetic file before listening. The route reserves fixed extraction work after original registration and withholds the receipt if that reservation fails. A separate [document-processing journal](processing-journal.md) grants exclusive expiring worker leases, reclaims expired work, and rejects stale completion tokens. A [serial scheduler](processing-scheduler.md) invokes the one-job worker after guarded startup enables private original storage and stops before the database pool closes. The case page polls validated active processing status and stops safely at terminal or unavailable results. Parser work remains inside the server process. Periodic recovery and directory synchronization remain incomplete. The next milestones are broader transfer qualification and source provenance. None of these milestones alone completes the upload-to-review features.
